# deps/locked-install

Installs use the lockfile strictly

A capability: each stack checks it with its own tools. Implemented for [dotnet](deps--locked-install--dotnet.md), [flutter](deps--locked-install--flutter.md), [go](deps--locked-install--go.md), [hugo](deps--locked-install--hugo.md), [java](deps--locked-install--java.md), [kotlin](deps--locked-install--kotlin.md), [node](deps--locked-install--node.md), [php](deps--locked-install--php.md), [python](deps--locked-install--python.md), [ruby](deps--locked-install--ruby.md), [rust](deps--locked-install--rust.md).

## Requirement

A task-runner recipe or a CI step installs (or verifies) dependencies in the package manager's locked mode, which fails when the lockfile and the manifest disagree instead of resolving new versions, and no recipe or CI step installs in a mode that rewrites the lockfile. Recipes of targets named for updating (update, upgrade, lock, bump) are exempt; comments and `echo` lines do not count. For a workspace member the repository's CI counts, and a parent directory's Makefile, justfile or Taskfile counts for the locked install.

## Why

An install that quietly re-resolves builds and tests something other than what the lockfile in git says, and the drift shows up only in production.

## Fix

Use the locked install in CI and in the check targets (npm ci, uv sync --locked, cargo --locked, ...).

Agent instruction: Switch the CI and task-runner installs to the package manager's locked mode; if that fails, regenerate the lockfile in a separate commit rather than relaxing the install.
